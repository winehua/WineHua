# 代码规范

> 适用场景：写新代码、改老代码、审查别人的改动时。
> 最后核实：2026-09-24
> 相关文档：[workflow.md](workflow.md)（协作流程）、[quality.md](quality.md)（验证要求）、[../architecture/contracts.md](../architecture/contracts.md)（跨仓库协议）、[../debugging/observability.md](../debugging/observability.md)（日志标签速查）

## 注释写当前有效的设计和理由

注释回答两个问题：**这是什么**、**为什么这么设计**。不写改动过程。

```cpp
// 反例：记录了一段历史
// 原来用 A 方案，实测有问题，改成 B，后来发现 B 也不行，最后用现在这个

// 正例：说明当前的做法和理由
// OHOS 的 musl 不带 locale 数据，不补 LC_ALL 的话中文程序会走到英文分支
```

过程属于提交记录，不属于注释。曾经的弯路压成一句结论式的提醒（「不要改成 X，因为 Y」），读代码的人需要知道的是「现在为什么是这样」和「什么不能动」。

还有一条：**不要写「与某处同源」「与某处保持一致」**。这种注释等于把知识拆成两半，改的时候必须同时找到两个地方。要么把判断抽成一个函数让两边都调用，要么在注释里直接写明这里是唯一实现。

## 日志要能查问题，但不能淹没日志

### 标签

原生代码用编译期定义的标签（`LOG_TAG`），界面层用消息前缀。完整的标签表在 [../debugging/observability.md](../debugging/observability.md)，写代码时掌握两条：

- 每个模块有专属标签（`WL_Seat`、`WL_EGL`、`WL_GFX`……）。
- 协议层统一用 `WL_Server`，因为系统日志的过滤粒度太粗，模块内部靠**消息前缀**再分（`[MW-TAKE]`、`[MW-SUBSURF]`、`[XDG]`……）。

### 降采样

**每一帧、每一次移动都打的日志必须降采样**，否则日志量会把系统的日志缓冲区冲掉，真正要看的内容反而没了（实测缓冲区只能留两三分钟）。

两种常用写法：

```cpp
// 每 N 次打一条（注意 N 的取值，注释里写清对应多少秒）
if (++tick % 600 == 0) OH_LOG_INFO(LOG_APP, "资源快照: ...");

// 第一次必打，之后按周期打——错误类日志用这种，避免"第一次出错看不到"
if (failures == 1 || failures % 60 == 0) OH_LOG_WARN(LOG_APP, "失败 %{public}d 次", failures);
```

抽样条件旁边要留注释说明「测试需要看全量时去掉这里」——找不到抽样点会误判成「没有触发」。

### 脱敏

系统日志会把参数当隐私处理，**格式串里的参数要加 `%{public}`**：

```cpp
OH_LOG_INFO(LOG_APP, "尺寸 %{public}dx%{public}d", w, h);   // 不加就是 <private>
```

浮点数尤其要注意——不加前缀时打出来是 `<private>`，数字完全看不到。

### 插桩随用随删

排查问题时临时加的日志（`[DIAG-xxx]` 这类）**用完就删**，或者单独提交一次（方便整体回退）。不要留在代码里变成长期噪音。留下的是有长期价值的诊断日志，那些要与降采样、`%{public}` 一起检查。

### Wine 内部的日志

- 默认 `WINEDEBUG=-all`（全关）。要开某个通道，改 `entry/src/main/cpp/proc/wine_child.cpp` 的 `select_winedebug_profile()`——走 `wine_env.cpp` 下发会被它盖掉。
- **`WINEDEBUG` 不能走环境变量注入通道**，会被覆盖。Wine 侧的唯一决策点在 `wine_child.cpp`。
- Wine 的 stderr 既写沙箱里的文件、也转发到 hilog（标签 `WineChild-stderr`），但转发不保证可靠，排障以文件为准（见 [../debugging/observability.md](../debugging/observability.md)）。

## 命名跟现有代码保持一致

| 位置 | 风格 | 例子 |
|---|---|---|
| C++ 文件名、目录名 | 全小写加下划线 | `wayland_server.cpp`、`toplevel_manager.h`、`compositor/toplevel/` |
| C++ 类名、方法名 | 每个词首字母大写 | `ToplevelManager`、`HasFrame()`、`IsToplevelVisibleLocked()` |
| C++ 成员变量 | 尾部加下划线 | `pixels_`、`toplevelMutex_`、`toplevelZOrder_` |
| ArkTS 文件名 | 每个词首字母大写 | `WineWindow.ets`、`WineEnvironmentService.ets` |
| ArkTS 常量 | 全大写加下划线 | `DOMAIN`、`MODE_VIRTUAL` |

**函数名加 `Locked` 后缀表示「调用之前必须已经持有那把锁」**。这是给读代码的人看的，也是给自己排死锁时用的——不带这个后缀的函数自己去拿锁，带了的不拿。混用的后果是自死锁（同一把锁不可重入，持锁状态下调用任何可能再拿同一把锁的函数都会卡住，日志函数也算）。

ArkTS 侧有静态检查（根目录的 `code-linter.json5`，覆盖 `**/*.ets`，用的是性能和类型检查的推荐规则）；C++ 侧没有配置静态检查，靠编译器和代码审查。

## 同一个判断只留一份实现

同一条规则在两处各写一遍，早晚会分叉——比如「全屏内容是否被遮挡」这个判断，两处各写一遍，直传那条路径就会漏掉浮层的情况，菜单被画面盖住点不到。

做法：

- 判据抽成一个函数，两边都调用它。
- 长表达式在代码里出现第二次时就该封装。
- 类里被多处读的字段，考虑收成私有的、由方法统一管（见下一节）。

## 状态交给类去管

窗口状态（位置、尺寸、像素、最小化标记等）都放在 `ToplevelManager` 里，**字段是私有的**，只能通过方法读写。这不是为了好看——是让编译器帮着守纪律：想在别处直接改一个字段，编译不过，只能去写一个语义明确的方法。

同样的做法也用在别的地方：

- 叠放顺序表只有一份（`toplevelZOrder_`），其他地方不许另存一份。
- 会话级状态集中在一个结构里（`DesktopSessionState`），各组件拿引用。
- 新模块不许自己另起一套锁，`toplevelMutex_` 是唯一的外层锁。

## 跨仓库的协议不能随便改

合成器、Wine 的显示驱动、Mesa、virglrenderer 之间有一批私有协议（共享内存页、present 命令、回调函数等），完整清单在 [../architecture/contracts.md](../architecture/contracts.md)。改这些协议要守五条：

1. **改了格式必须升版本号**。版本号是「我认不出你」的唯一报警通道，不升版本号的话，新旧两端撞在一起会造成难以定位的怪现象。
2. **对端必须同步改**，改完跑两个平台的全量回归。改哪个协议要动哪些仓库，契约文档里逐个写着。
3. **同步更新契约文档和对应的 submodule 补丁清单**（`docs/assets/submodules/`）。前者记录「整条协议长什么样」，后者记录「这个仓库改了协议的哪一版」。
4. **魔数、版本、长度、序号四样缺一不可**：文件或数据包的标识、格式版本、字段个数、请求与回复的配对。
5. **先写文档再写代码**。两端各自开工之前，先把格式定稿到契约文档里，避免实现期间两边各改各的。

## 能在界面层解决，就不要写原生代码

遇到能力问题（需要某个系统功能、某个交互效果），**先查 ArkTS 的 `@ohos.*` 接口**。界面的东西尽量在界面层解决，原生代码走原生通道的代价是跨语言调试、跨进程通信、还要自己管生命周期。

只有界面层确实覆盖不了的才引原生：需要直接接触 GPU 的渲染、性能关键路径、系统未开放的能力。

## 其他约定

- **构建只能走根目录的 Makefile**，它是唯一的构建入口。不要在子目录里单独调构建工具，会产生构建目录错乱、产物过期这类问题。
- **产品代码不引用测试程序**，测试用的 exe 不放进 Wine 的 `bin/` 目录。测试载荷走独立的目录树。
- **Wine 资源文件（`.rc`）里的逐行字符串要各写各的引号**。多行拼一个字符串字面量会报「Unterminated string」，问题还不好找。改完先单独构建那一个资源文件快速验证，比整包构建快得多。
- **资源文件编译要带 Unicode 参数**。漏掉的话资源会被编成 ANSI，主题之类的功能静默失效——不报错，只是不生效，很难查。
