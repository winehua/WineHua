# 故障现场取证

> 适用场景：进程还活着但不动（死循环、卡死），或者崩溃了但拿不到栈——需要在**进程内部**把现场抓出来时。
> 最后核实：2026-09-25
> 性质说明：本文写的是"抓什么、怎么看"，属于做法和原理层面；具体落在哪份实现上，按当时的代码状态去查。
> 相关代码：`thirdparty/box64/src/dynarec/arm64/arm64_mapping.h`（寄存器映射）、`thirdparty/box64/src/emu/x64emu_private.h`（emu 结构布局）、`thirdparty/box64/src/include/env.h`（调试开关表）
> 相关文档：[observability.md](observability.md)（日志通道、崩溃定位）、[troubleshooting.md](troubleshooting.md)（按症状排查）、[performance.md](performance.md)（性能与对比实验）

## 1. 什么时候用这篇

| 症状 | 看哪一节 |
|---|---|
| 画面静止 / 白屏，进程还在 | 先做第 2 节（自旋还是阻塞），再按结果走第 3、4 节 |
| 进程在同一个地址上反复报错 | 第 3 节的 fault 记录 + 第 5 节的地址对照 |
| 进程没反应但没崩溃 | 第 3 节的卡死看门狗 |
| 怀疑"卡在翻译出来的代码里" | 第 4 节（从寄存器还原 guest 位置）+ 第 6 节（翻译器开关） |
| 想把一个怀疑的机制证实/证伪 | 第 7 节（最小复现探针） |
| 怀疑"这到底是不是我们的 bug" | 第 8 节（上游对照法） |

前提：先按 [observability.md](observability.md) 把日志通道准备好。**从进程外面读 `/proc/<pid>/maps`、`mem`、`stack` 都拿不到**（`Operation not permitted` / SELinux 拒绝），所以地址性质、栈内容这些只能在**进程内**取。这是本文所有做法都要求在进程内埋点的根本原因。

进程内的输出落地要自己安排：`write(2)` 到 stderr 会进沙箱的 `temp/wine_stderr_YYYYMMDD.log`，同时被转发到 hilog（标签 `WineChild-stderr`）——但转发不保证可靠，排障以沙箱里的文件为准。

**注意两套 PID 命名空间**：窗口相关 API 返回的是 Wine（guest）PID，而信号类日志里的 pid/tid 是**宿主 PID**。对不上号时先确认自己在哪一侧。

## 2. 第一步：判"自旋"还是"阻塞"

两类问题的排查方向完全不同，先花 10 秒定性。

```bash
D=<设备IP>

# 找进程（应用主进程 + guest 游戏进程，后者是前者的子进程）
hdc -t $D shell "ps -ef | grep -iE 'winehua|\.exe'"

# 状态：第 3 个字段（R=运行 S=睡眠 D=不可中断）
hdc -t $D shell "cat /proc/<PID>/stat | cut -c1-60"

# 时间：第 14/15 字段（utime/stime，tick）；间隔 3 秒采两次
hdc -t $D shell "A=\$(cut -d' ' -f14,15 /proc/<PID>/stat); sleep 3; \
                 B=\$(cut -d' ' -f14,15 /proc/<PID>/stat); echo \$A; echo \$B"
```

| 观察 | 结论 | 下一步 |
|---|---|---|
| 时间在涨 + 状态 `R` | **自旋**（在算，但出不来） | 第 3 节抓现场 |
| 时间不涨 + 状态 `S` | **阻塞**（等锁、等 IO、等事件） | 看"卡死前的最后一条日志"（见 [troubleshooting.md](troubleshooting.md) 卡死一节） |

线程级定位（哪个线程在转）：

```bash
hdc -t $D shell "ls /proc/<PID>/task/ | while read t; do cat /proc/<PID>/task/\$t/stat; done | cut -d' ' -f1-3"
```

> 设备 shell 极简：**没有 `awk`**，通配符不展开，用 `cut`/`grep`。线程列表也可以用 `hidumper -p <pid>` 一次列全。

## 3. 进程内要抓什么

四类现场，分别对应四种"从外面看不到"的情况。

### 3.1 进程最早处的崩溃

宿主 linker（ld-musl）阶段的崩溃发生在 Wine 自己的信号链装上之前，Wine 侧完全看不到。要在**进程最早的初始化处**挂信号处理器，并且**只记录、不接管**——不改上下文、不吞信号，否则会干扰后面正常的信号处理。

要记的：信号号 + `si_code`、故障地址 `si_addr`、pc / lr / sp、完整寄存器、故障指令附近的机器码（用来反汇编看当时执行的是哪条指令），以及把这些地址各自归因到模块（见 3.2）。

**配额要按 `(信号, pc)` 分组去重。** 启动期固定会打几颗探针信号——每个 x64 进程启动时都有几颗 SIGBUS 探针——如果"前 N 颗全打"，配额会被这些噪音吃光，真正致命的那颗反而漏了。

### 3.2 地址归因

把 pc / lr / sp / 故障地址分别对到 `/proc/self/maps` 的具体 VMA 行，输出命中那一行，或者"不在任何映射里"（附前后两条邻居，用来判 guard 页）。

**踩过的坑**：`/proc/self/maps` **单次 `read()` 会在 4 KB 的 seq_file 边界截断**（实测只拿到 ~3.5 KB，读到高位区就停），导致高位地址全被误判成"不在映射里"。必须循环读到 EOF。

### 3.3 卡死看门狗

判据用**低占用**，不是"CPU 零增长"：窗口内 utime+stime 的增量低于"窗口时长 × 1 tick"（约一核的 10%）。拿零增长当判据会漏掉"在慢慢转"的情况。

线程级现场靠**采样**拿：

- 采样间隔留 ~20 ms，否则阻塞在 futex 上的线程收不到信号
- 采样 handler **必须链式调用旧 handler**，否则会把别人的采样器顶掉
- 每个线程记 comm、wchan，以及采样到的 pc / lr / fp 归因

### 3.4 翻译器 fault 路由上该看什么

翻译器（box64 / FEX）在 guest 指令触发访问异常时也会进场。这条链上有几个维度必须记：

| 维度 | 用途 |
|---|---|
| 信号号 + `si_code` | `SIGSEGV` + `SEGV_ACCERR` = **地址有映射但没权限**；未映射是另一类。这一条就能把"映射被搞坏了"和"访问了未提交区"分开 |
| `si_addr` | 故障**访问**的地址（不是 PC） |
| 宿主 PC | 落在匿名 JIT 映射里 = 故障发生在翻译出来的代码中 |
| guest RIP / emu 指针 | 见第 4 节 |
| 注册进来的 handler 地址 | 0 表示没有翻译器注册，这条链就与翻译器无关 |
| 故障地址所在 VMA 的权限串 | `---` = 保留 / 未提交区 |
| pc 是否在 dynablock 内 | 区分"翻译出来的代码"和"翻译器自己的代码" |
| 处理结果 | 谁认领了这次 fault：翻译器自己 / Wine 的 SEH / 不是我的 / 继续往下传 |

配套还要有：地址归属、前后各几条 VMA（判 guard 页）、往代码页写（自修改代码）、调用返回类指令的异常。

**限流要成对设计**：前若干条全打、之后每 N 条一条。这样"反复出现的同一行"本身就说明在转圈。**别用日志行数推断频率**——被限流之后行数说明不了任何事。

## 4. 从宿主现场还原 guest 状态（关键技巧）

**`x27` = guest RIP 是寄存器约定，不是查表**：翻译器把 guest 的 x86 RIP 固定放在宿主寄存器 x27（box64 arm64 后端 `src/dynarec/arm64/arm64_mapping.h` 里 `#define xRIP 27`）。所以任何一次宿主信号现场，**x27 就是 guest 侧当前指令地址**，对着该 exe 的映像基址一减就知道落在哪里。FEX 的 ARM64EC 路径同样用 x27 保存 guest RIP。

**要更完整的 guest 现场**：`x0` 就是 emu 上下文指针，其内存布局是稳定的——

| 偏移 | 内容 |
|---|---|
| `+0x00` 起 16×u64 | x86 通用寄存器（rax / rcx / rdx / rbx / rsp / rbp / rsi / rdi / r8-r15） |
| `+0x80` | flags |
| `+0x88` | guest RIP |

按这个布局就能把 guest 的寄存器、标志位、指令指针一次性读出来。

## 5. 判断"这个地址正常吗"——三层对照

缺一层就可能误判：

1. **guest 视角**：枚举目标进程的内存表（`VirtualQueryEx` 一类）→ 是 `MEM_RESERVE` 未提交？已提交但无权限？还是根本没有映射？
2. **宿主视角**：maps 里的权限串；页上有没有"这是 dynarec 代码"的标志位。
3. **源码视角**：对照 guest 指令本身在干什么（例如 `dec ecx` → 跨页的 `mov` → `jne`），看**预期**应该落在哪个区间。

常见的误判是用第 2 层就下结论：一个地址看着像"映射被保护驱动破坏了"，用第 1 层一查才发现它本来就是**正常的 `MEM_RESERVE` 未提交区**——访问它说明代码走错了，不是映射坏了，方向整个翻过来。

## 6. 翻译器侧的开关（box64）

| 变量 | 取值 | 作用 |
|---|---|---|
| `BOX64_DYNAREC_DUMP` | 0–2 | dump 每个 dynablock 的翻译结果 |
| `BOX64_DYNAREC_DUMP_RANGE` | `0xAAAA-0xBBBB` | 只 dump 指定区间（防刷屏） |
| `BOX64_DYNAREC_LOG` | 0–3 | 日志详略 |
| `BOX64_LOG` | 0–3 | 总日志 |
| `BOX64_SHOWSEGV` | 0/1 | 段错误信息 |

**调档位做 A/B**（分辨"是不是块边界/标志位处理的问题"）：`BOX64_DYNAREC_BIGBLOCK`（0–3）、`SAFEFLAGS`、`NATIVEFLAGS`、`CALLRET`、`STRONGMEM`。档位表见界面层的 `Box64Dynarec.ets`。

**手法**：换 `BIGBLOCK` 档位后如果**故障地址跟着变**，说明问题与"块怎么切"强相关，而不是地址空间问题；再关掉 `NATIVEFLAGS` 看是否仍复现，可以排除"本机标志优化"这条支路。

> 环境变量下发的两个坑：某些变量在 env 应用**之前**就被读取（配了不生效，见 [troubleshooting.md](troubleshooting.md)）；在 wine 会话里用 `cmd set` 设的变量**不会**传到子进程。

## 7. 最小复现探针（最值得学的一招）

怀疑某个机制时，别在真实程序里猜——写一个几十行的自包含 PE：构造条件 → 自己判定 PASS/FAIL → 结果写到文件。

构造的关键是**把怀疑的机制逼到极限**。举例：要验证"跨页分支上的标志位处理"，就分配 8 KB 可执行内存，把循环体放在第一页末尾、把条件跳转放在第二页开头，再把整区改成只读（逼翻译器在页边界截断块），最后断言循环次数必须恰好等于预期值。

三条纪律：

- **自判定**：探针自己写 PASS/FAIL，别靠人看日志。
- **只看它自己落盘的文件**：宿主返回码（比如 `exit=11`）**不等于**失败，用返回码判断会得出相反结论。
- **要能进回归**：同一个探针既用于一次定位，也挂进自动化套件防复发。

## 8. 两条方法

**证据链的推进顺序**（故障排查的通用次序，每一步都要落到具体数据上）：

1. **定性**：自旋还是阻塞（第 2 节）——先排除"根本不是计算问题"的方向
2. **找现场**：反复出现的 fault 日志 → 拿到故障地址 + 宿主 PC + guest RIP
3. **判地址性质**：三层对照（第 5 节）——这一步最容易被跳过，也最容易翻盘
4. **算量**：看现场里的计数、指针离预期差多远（差得离谱 = 该停的没停，或该做的没做）
5. **看真实指令**：反汇编 guest 指令 + dump 该处翻译后的机器码，比对"应该做什么"和"实际做了什么"
6. **排除法**：关掉相关优化 / 换档位，看现象是否跟着变（跟着变 = 收敛到那个机制）
7. **修 + 立回归探针**（第 7 节）

价值在于：**不是靠读代码猜，是靠"内存是否正常 → 计数是否离谱 → 指令在哪跨页 → 机器码里到底生成了什么"一步步逼出来的。**

**上游对照法**：判"这到底是不是我们的 bug"，直接拉上游同段代码对比，别凭印象：

```bash
mkdir -p /tmp/up && cd /tmp/up && git init -q
git remote add up git@github.com:<上游仓库>
git fetch --depth=1 up main
git show FETCH_HEAD:<路径> | grep -n -A3 '<关键标识>'
```

> 两个坑：在浅克隆（shallow）里跑 `git log -S` 会给出**假答案**（可能把几段不同历史都归到同一个"根提交"）；判某个分支有没有某个修复，要读 pin 上的**文件内容**（`git show <sha>:<路径>`），而不是看提交标题。

## 9. 坑清单

| 坑 | 现象 | 正确做法 |
|---|---|---|
| 环境变量下发 | 配了但没生效（在 env 应用之前就被读走） | 确认读取时机；对照实验前先确认开关真的生效（[performance.md](performance.md) 有同样提醒） |
| wine 会话里 `cmd set` | 变量传不到子进程 | 走应用侧的下发通道 |
| 信号处理器里解引用地址 | 二次 fault → `nested exception on signal stack` → 进程直接 abort | 先校验 VMA 可读，或用内核拷贝（`process_vm_readv`）读栈 |
| `/proc/self/maps` 单次 read | 高位地址被误判"不在映射" | 循环读到 EOF |
| 打点配额 | 启动期的固定探针信号占满配额，真故障没记下 | 按 `(信号, pc)` 分槽去重 |
| 采样 handler | 把别人的采样器顶掉 | 链式调用旧 handler |
| 探针返回码 | `exit=11` 被当成失败 | 只看探针自己落的文件 |
| 日志限流 | 以为"只发生了几次" | 早期全打、之后每 N 条一条，别用行数推断频率 |
| 外部读 `/proc/<pid>/{maps,mem,stack}` | `Operation not permitted` | 全部改为进程内取 |
| 调试器 | 设备上没有 gdb/lldb，winedbg 也不能用 | 用进程内探针 + 外部采样（[performance.md](performance.md)） |
| 诊断改动混进基线 | 临时打点被当成修复提交 | 诊断代码单独成补丁，定位完就摘掉 |
