# 问题排查索引

> 适用场景：遇到具体症状时，先来这里查"从哪下手"。每条给出排查方向和已知原因。
> 最后核实：2026-09-24
> 相关文档：[observability.md](observability.md)（日志通道与标签）、[performance.md](performance.md)（性能问题）、[../architecture/graphics-matrix.md](../architecture/graphics-matrix.md)（图形档位）

## 通用思路

1. **先确认问题在宿主还是在 Wine**。最省事的判据是"帧提交日志（`MW-COMMIT`）有没有断流"——断流说明 Wine 不再提交画面，问题在那一边。
2. **按链路找断点**。输入问题看 [input.md](../architecture/input.md) 的日志分布表；图形问题看 [graphics-matrix.md](../architecture/graphics-matrix.md) 的通道划分。
3. **对照实验优先**。怀疑是平台问题时，先在普通 Linux 上跑同一个程序做对照。
4. **注意历史记录**。有些问题下面标注了"已修复"，如果又出现，看看是不是同一条原因；标注"未解决"的，说明至今没有根因。

## 白屏

| 现象 | 排查方向 | 已知原因 |
|---|---|---|
| 多窗口模式点/拖标题栏后画面全白 | 抓屏看画面内容；dump 系统窗口层级看叠放顺序 | 系统点击可聚焦子窗口时自动置顶，把画面窗口盖住了。修法是整组提升（主窗口和画面窗口一起） |
| D3D12 程序全白屏（画面已到达宿主） | 对比 master 和 main-ui 分支的行为 | **未解决**。两个分支表现不同，怀疑界面层的画面承载拓扑差异 |

## 黑屏

| 现象 | 排查方向 | 已知原因 |
|---|---|---|
| 测试用例报"帧数正常"但画面是黑的 | 加画面内容判定（非背景像素占比、画面是否在变化） | 帧数正常不代表渲染正确——这是判定能力的缺口，不是新 bug |
| 全屏时左右黑边、画面被纵向拉伸 | 对比组件声明的尺寸和渲染器读到的实际尺寸 | 画面缓冲偶尔停在系统的中间状态尺寸（系统栏高度那一档），渲染器按这个错误尺寸做了等比缩放，系统再把它非等比拉伸到全屏。**卡住后不能自愈** |
| D3D12 黑屏 | 检查内存同步档位 | vkd3d 只能用 dirty-ring 档，用 explicit 档必然黑屏 |

## 花屏 / 贴图错误

| 现象 | 排查方向 | 已知原因 |
|---|---|---|
| 贴图花屏或首帧数据丢失 | 打开着色器追踪，对比 guest 和宿主的内存指纹 | 影子内存同步丢失（宿主侧的内存同步链路有已知的复杂问题） |
| 特定程序的贴图错乱 | 用状态追踪对比各阶段的数据 | 遇到过设备驱动编译器对布尔常量的处理问题，有对应的规避开关 |

## 卡死

先分类，两类卡死的排查方向完全不同：

**冻结型**（游戏跑起来了，然后冻结）：
- 判据：帧提交断流，但进程都活着。
- 常见原因：① 渲染线程卡死（宿主渲染日志停更）；② 旧的 Wine prefix 残留状态（清 prefix 重试）。

**死寂型**（窗口从来没创建出来）：
- 判据：屏幕上什么都没有，也没有窗口创建日志。
- 常见原因：启动链路上的死锁——比如某个锁被持有后重复获取（同一把锁不可重入，持锁时调用任何可能再次拿同一把锁的函数都会自死锁）。这类问题的定位方法是看"卡死前的最后一条日志"。

**其他卡死情况**：
- 整机冻结（连系统界面都卡）：看崩溃记录里有没有应用冻结（appfreeze）；审查代码里有没有"持锁做跨进程调用"的结构。
- 首启卡在启动画面：先看是不是引擎初始化卡住了（首启要做完整的 prefix 初始化，比二次启动慢很多）。

**先分清"自旋"还是"阻塞"**（时间在涨+状态 R = 自旋；不涨+状态 S = 阻塞），以及自旋时怎么把现场抓出来，见 [fault-forensics.md](fault-forensics.md)。

## 闪退

| 现象 | 排查方向 | 已知原因 |
|---|---|---|
| 手机"停止/重启引擎"必崩 | 只在虚拟桌面 + 手机模式出现 | 图形库在渲染上下文销毁后解析函数指针导致中止。修复 = 缓存函数指针 |
| 首次启动偶发崩溃或卡住数分钟 | 看 Wine 标准错误文件里的崩溃信息 | 转译层（box64）的缺陷——这个转译器有若干已知问题，项目里对应挂了几处环境变量规避，都是止血不是治本 |
| 开鸿设备首次启动崩溃 | 看是否能执行到内存保护相关代码 | 鸿蒙的内存权限规则导致（见 [../architecture/platform-ohos.md](../architecture/platform-ohos.md)）。已修复 |
| 宿主进程闪退 | 按 [observability.md](observability.md) 的崩溃定位五步 | 先查 Faultlogger（有持久化记录），再从进程存活曲线判断是宿主还是 guest；拿不到栈就转锁纪律审查 |

## 点击无响应

| 现象 | 排查方向 | 已知原因 |
|---|---|---|
| 模态对话框点不动 | 确认输入链路是否完整（日志全链路） | **未解决**，原因未定位，2026-09 起暂停排查 |
| 某些程序的弹窗点不动 | 看该程序的子进程是否崩溃 | 转译层加载 32 位组件时崩溃，UI 线程跟着死了 |
| 第一次点击无效、第二次有效 | 看相对指针对象是否被误创建 | 桌面进程被误判进入相对模式，跳过了跨窗口的进入事件。已修（限同窗口才跳过） |
| 点击位置偏移 | 对比注入坐标和视觉位置 | 直传模式下坐标被二次缩放。已修 |
| 菜单弹不出来（开鸿 PC） | 看创建子窗口的返回码 | 该系统不支持子窗口。决策：统一用虚拟桌面 |

## 其他常见问题

| 现象 | 排查方向 |
|---|---|
| 窗口拖不动 / 改不了大小 | 看几何与尺寸映射日志（`MW-GEO` / `MW-RESIZE`），确认窗口的最大最小尺寸限制是否相等 |
| 窗口改变大小后画面不刷新 | 已修（尺寸变化强制重绘，不让旧内容被拉伸显示） |
| 热重启后桌面被裁掉一部分 | 检查输出尺寸有没有被窗口尺寸变化污染。**输出尺寸只由界面层设置** |
| 应用库图标全变默认 | 清缓存前先查谁把图标路径持久化了——路径失效导致 |
| 热重启后画面"慢一拍" | 检查渲染器有没有泄漏。状态要按会话重置 |
| 全屏被桌面窗口盖住 | 先看合成日志（`MW-RNDR`）确认叠放顺序。提窗口时不排除桌面根窗口是个结构隐患，靠合成和命中时排除根窗口兜住 |
| 某个开关改了没效果 | 先确认开关有没有真的下发到目标进程——有环境变量下发通道不可达的先例 |
