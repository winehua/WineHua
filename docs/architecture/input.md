# 输入链路

> 适用场景：改鼠标、键盘、触控相关代码前；排查"点了没反应""光标位置不对""拖动不跟手"这类问题时。
> 最后核实：2026-09-24
> 相关代码：`entry/src/main/cpp/input/`、`entry/src/main/cpp/compositor/input/`、`entry/src/main/ets/components/DesktopLayer.ets`、`WineWindow.ets`

## 整体结构

输入事件从系统的界面组件一路传到 Wine，中间分五段：

```
系统输入事件（界面组件的 onMouse / onTouch / onKeyEvent / onAxisEvent）
  → 界面层处理：手势识别、坐标换算（DesktopLayer.ets / WineWindow.ets）
  → NAPI 桥：转发到原生（bridge/napi_init.cpp，打 [PIPE] 日志）
  → 编排层：目标窗口裁决、状态跟踪、入队（input/input_manager.cpp）
  → 队列：跨线程传递 + 去重（compositor/input/input_queue.cpp）
  → 注入层：发 Wayland 协议（compositor/input/input_injector.cpp）
  → Wine（winewayland.drv 接收）
```

**为什么要分这么细**：前面四段跑在界面线程（NAPI 线程），最后一段必须在 Wayland 线程——`wl_pointer_send_*` 这类协议调用有线程要求，从别的线程调用会出问题。所以中间需要一个队列把两段接起来。

队列还顺带解决一个问题：界面层一次触摸滑动可能产生几百个移动事件，全发给 Wine 没有意义（Wine 按帧处理），所以入队时会**去重**——同一类移动事件只保留最新的一个坐标；按键和滚轮不做这种丢弃（每个都有意义）。

## 四条链路

### 鼠标

**界面层**（`DesktopLayer.ets` 虚拟桌面模式、`WineWindow.ets` 多窗口模式）：

- 移动事件：先判断手势状态机是否在进行中（进行中就跳过，避免和触摸事件重复发送），然后确定目标窗口——用按键按下时记录的窗口，或者按坐标查。
- 按下/抬起：按下时记录目标窗口并把它提到最前，抬起时释放。
- 有一个细节：物理左键按下时会把 `mouseLeftActive` 置位，用来**抑制系统为左键合成的触摸事件**。如果不抑制，合成的触摸会进手势状态机，把一次正常的点击压成 0 毫秒的脉冲，靠轮询读输入的老游戏就看不到这次点击（原因写在 `DesktopLayer.ets` 的注释里）。

**原生层**（`input_manager.cpp`）：

- 坐标换算：屏幕坐标 → 桌面坐标（虚拟桌面有缩放，要逆映射）。
- 目标裁决：按窗口叠放顺序从前往后找，找到第一个命中的窗口。
- 按键值定义：按下=1、抬起=2、移动=3。
- **脉冲拉伸**：按下和抬起间隔小于 100 毫秒的点击，会延迟抬起、把间隔补足到 100 毫秒再发。这是为触屏准备的——触屏的点击几乎是"按下即抬起"，补足后靠轮询的游戏才能看到。
- 按下时如果目标是新窗口，先发进入事件；键盘焦点跟着点击走（点哪个窗口，键盘就发给哪个窗口）。

### 键盘

1. 界面层收到按键，把系统键值转换成 Linux 键值（`KeyMap.ets` 的映射表，Wine 直接吃这套键值）。
2. 有一个兜底：系统软键盘或输入法有时只发抬起、不发按下，代码检测到"没有配对的抬起"时会补发一次按下+抬起。
3. 原生层处理焦点：非桌面模式下，如果按键的目标窗口还没获得焦点，先发离开/进入事件切换焦点；**桌面模式下键盘永远发给桌面根窗口**，不覆盖点击建立的焦点。
4. 注入时只发给已经获得焦点的客户端（避免无效投递）。

键盘布局数据（XKB）通过共享内存传给 Wine，重复按键参数是 40 毫秒延迟、400 毫秒间隔（按住不放时每 400 毫秒重复一次）。

### 滚轮

- 物理滚轮：多窗口模式挂在窗口组件上，虚拟桌面模式按光标位置找目标窗口。
- 触摸板双指滚动：两指中点每移动 40 个物理像素，发一个离散滚动步。
- 协议上发两个事件：离散步数 + 连续值。Wine 侧的重叠窗口驱动只处理离散事件，所以离散步数不能省。
- 滚轮事件**不去重**（每个值都是累计滚动量，丢掉中间值就等于丢滚动距离）。

### 修饰键

按下 Ctrl、Alt、Shift、Meta 时，除了发按键本身，还要同步发一次"当前修饰键状态"。这一步单独做是因为：

- Wine 需要知道 Shift 是否按下这种状态，才能正确解释后续按键。
- 每次修饰键变化都发一次；键盘焦点切换时也发当前状态；会话结束时清空——**不清空会导致 Ctrl 卡在按下状态，跨会话污染**。

CapsLock 和 NumLock 的处理不同：它们是按一次切换一次（锁定状态），不是按住有效。

## 相对指针模式

**要解决的问题**：第一人称游戏需要"无限移动"的鼠标输入——光标藏起来、鼠标往一个方向推就持续转向。用绝对坐标做不到（光标推到屏幕边缘就不动了）。

**什么时候进入**：由 **Wine 侧判断**——它发现光标被隐藏、并且锁定约束落在当前聚焦窗口上，就创建相对指针对象。宿主侧不做模式判断，收到请求就切换。

判断权完全交给 Wine 侧，宿主侧不做模式判断。

**宿主侧要做的**：始终发绝对移动（有些游戏需要），**同时**额外发一份移动增量。增量优先用硬件上报的原始位移（光标被钳在边缘时，"两次绝对坐标的差"会恒等于 0，原始位移则一直有效）。

**几个坑**：

1. **冻结的触发点不是锁定约束，是相对指针对象**。按锁定约束去冻结会误伤红警2 主菜单这类窗口——光标可见、但恰好挂了约束。
2. **相对模式下的点击会瞬移**。因为按下时会重发一次带绝对坐标的进入事件，Wine 会把光标挪过去。修法是 Wine 侧加了一个静默路径：进入事件只更新 Wine 内部记录的光标位置，不产生真实输入。
3. **桌面进程可能被误判进相对模式**，导致第一次点击落到别的窗口。宿主侧加了守卫：只有在目标窗口和当前焦点窗口相同时才跳过进入事件。

## 触控板模式

把触摸屏当触控板用（悬浮条上的开关）。与直接触控是两套完全不同的语义，不能混：

- **直接触控**：指哪点哪（绝对定位）。
- **触控板模式**：光标在哪点哪（手指相对位移驱动光标，点按作用于光标位置）。

开启后直接触控的状态机整体旁路。手势表：

| 手势 | 判定 | 行为 |
|---|---|---|
| 单指滑动 | 位移超过 10 物理像素 | 移动虚拟光标（速度可调），光标钳在屏幕内 |
| 轻点 | 未超阈值且时长小于 500 毫秒 | 光标处左键点击 |
| 长按 | 未超阈值且时长达到 500 毫秒 | 光标处右键 |
| 双击后按住拖动 | 第二次按下距上次点击小于 400 毫秒 | 光标处按下左键并跟随移动，抬起时释放 |
| 双指拖动 | 两个手指 | 滚动（作用于光标所在窗口） |

## 光标显示与隐藏

先说结论：**隐藏光标的能力只有界面层有，冻结光标的能力只有原生层有**，所以两件事要分别判断、协同动作。

触发链：Wine 请求相对模式 → 原生层冻结系统光标（调用系统接口）→ 通知界面层 → 界面层判断"这个窗口该不该隐藏光标" → 决定是否隐藏。

判断条件（界面层）：多窗口模式允许；虚拟桌面上，如果当前是"桌面壳"（桌面自己的窗口）则禁止，游戏窗口允许；桌面还没就绪时禁止。

**两个必须记住的教训**：

1. **冻结和隐藏必须用同一套判断条件**。有一次只拦了隐藏、没拦冻结，结果是"光标还在屏幕上但完全动不了"——比不隐藏更糟。
2. **桌面还没就绪时不能冻结**。桌面窗口的标识在就绪前是 0，会导致判断失效、桌面壳被当成游戏冻结。现在的代码有专门的时序判断（看桌面根窗口是否已就绪）。

## 输入法

采用组合方式：原生层补一个文本输入协议（Wine 需要它才能用输入法），界面层用系统的输入法接口对接。

流程要点：

1. 键盘焦点切到某个窗口时，原生层按客户端把文本输入对象路由过去（**每个 Wine 进程各有自己的对象，发错对象收不到输入**）。
2. Wine 收到后启用；**真正的激活信号是光标矩形非零**——窗口聚焦时也会发一次启用，但此时矩形是 0，不能当成激活。
3. 激活后界面层接管输入法控制器：先注销旧的监听、再挂载、再注册新监听（顺序不能反，也不能不注销——不注销会导致一次输入触发多次）。
4. 上屏文字、预上屏文字、退格都有对应通道。**退格是特殊处理的**：Wine 侧的"删除指定范围文字"接口是空实现，所以退格走的是键盘退格键注入。
5. 失焦时注销监听。

## 排查手段

输入问题排查靠日志，关键是找到"链路断在哪一段"。日志按段分布：

| 段 | 日志标签 | 看什么 |
|---|---|---|
| 界面层 | `CLICK-PIPE` / `KBD-PIPE` | 事件有没有从界面层发出、手势判定结果 |
| NAPI 桥 | `WL_NAPI` 的 `[PIPE]` | 有没有到原生层 |
| 编排层 | `WL_Input` 的 `[Input]` | 坐标换算、目标窗口裁决、相对增量计算 |
| 扩展协议 | `WL_PtrExt` | 相对模式对象创建、光标锁定、增量广播 |
| 注入层 | `WL_Input` 的 `Inject*` | 协议有没有真的发出去 |
| 丢帧统计 | `Input-DROP` | 每 60 秒汇总一次丢弃情况 |

移动类日志默认按 1/120 抽样（否则日志会被刷爆），按键、滚轮、注入是全量。要临时看全量，把对应位置的抽样条件去掉。

**排查方法**：复现问题后，按上面的顺序看日志，找到第一条缺失的日志，问题就在它前一段。死锁类问题看"卡死前最后一条日志"，那就是最后一跳。

## 已知问题

1. **桌面进程可能误入相对模式**：Wine 侧会误判（桌面 shell 设了约束时），目前靠宿主侧的守卫兜底。
2. **键盘避让**（输入法弹出时窗口上移）尚未实现。
3. 日志里出现 `STRETCH`（脉冲拉伸）说明有输入路径产生了"按下即抬起"的脉冲。物理鼠标不应该触发它——如果看到，说明某条路径有问题。
