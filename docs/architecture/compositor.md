# 合成器

> 适用场景：改窗口显示、画面合成、窗口叠放顺序相关代码前；排查"画面不对""窗口被盖住""桌面背景消失"这类问题时。
> 最后核实：2026-09-22
> 相关代码：`entry/src/main/cpp/compositor/`（frame/、toplevel/、input/ 三组 + 协议层文件）、`entry/src/main/cpp/graphics/egl_renderer.cpp`
> 相关文档：[contracts.md](contracts.md)（跨仓库协议）、[../decisions/0001-self-built-compositor.md](../decisions/0001-self-built-compositor.md)（为什么自研）

## 整体结构

合成器是自研的 Wayland 服务端，跑在应用主进程里。分三组：

| 目录 | 负责 |
|---|---|
| `frame/` | 帧合成：规划、绘制、显示策略、几何计算 |
| `toplevel/` | 窗口状态：窗口表、叠放顺序、桌面合成、根窗口识别、弹出菜单 |
| `input/` | 输入：队列、状态跟踪、注入、命中裁决、坐标映射 |

加上协议层的几个文件：`wl_core.cpp`（surface 与提交路径）、`xdg_shell.cpp`（窗口协议）、`wayland_server.cpp`（总装配）。

**状态归属**（改动时先搞清楚状态在谁手里）：

- 窗口状态（位置、尺寸、像素、最小化/全屏标记）都在 `ToplevelManager`，而且字段是私有的——只能通过方法读写，让编译器帮着守纪律。
- 叠放顺序表（`toplevelZOrder_`）是**唯一**的存放处，其他地方不许另存一份。
- 会话级状态（桌面根窗口标识、显示策略、输出尺寸、首帧标记）集中在一个结构里（`DesktopSessionState`），各组件持有引用。
- 锁的纪律：`toplevelMutex_` 是唯一的外层锁，新模块不许自己另起一套锁。

## 一帧画面怎么拼出来

### 画面来源

虚拟桌面模式下，一帧画面可能由这几种内容叠出来：桌面背景（根窗口自己的像素）、普通窗口、子表面（菜单、弹出内容）、GPU 画面（Zero-copy 的 GL 窗口）。

**统一之后，所有来源都是同一种东西**（`CompositorLayer`），按同一个列表、同一个顺序遍历——合成和输入命中用同一份列表。这是重构时定的规矩，避免"合成按一套顺序、输入按另一套顺序"这种经典 bug。

### 合成过程

分两段：

1. **锁内规划**（快速）：判断哪些内容变了、要不要走快路径、算出需要重绘的区域、把要用的像素快照出来。大约 1-3 毫秒。
2. **锁外绘制**（慢活）：按顺序把各个层画到输出帧上。放在锁外做。

**为什么要分开**：之前是持锁做完整帧的合成（约 25 毫秒），期间窗口提交会被堵住（实测平均堵 27 毫秒、最坏 90 毫秒）。拆开后锁占用降了一个数量级。

### 三条快路径

**无子窗口直通**：根窗口内容变了、但没有其他窗口或图层，直接把根窗口的像素作为输出，跳过全部合成。

**全屏直传**：全屏游戏画面直接从游戏的原始像素上传给 GPU 缩放显示，跳过整帧合成。这一条对性能影响最大——游戏原始分辨率（比如 800×600）直接上屏，省掉整帧 CPU 合成。走这条路要满足几个条件：全屏窗口之上没有可见内容（有弹窗就走不了）、窗口格式不透明、尺寸严格匹配。

**局部重绘**：只重画"内容确实变了"的层所覆盖的区域，其余部分复用上一帧。判断依据是每个层的内容版本号（提交时更新）。

## 窗口叠放顺序

顺序只在 `toplevelZOrder_` 这一处维护，每帧转成合成用的列表。排序规则：

1. **桌面根窗口永远在最底层**（它是合成的底，不是内容）。
2. **普通窗口按顺序排**，每个窗口和它的子表面成块，块内父窗口在前。
3. **模态对话框**在它的属主窗口那一块里，但序号从很大开始——效果是模态框永远在属主的所有内容之上。
4. **弹出菜单类**（父窗口是桌面根、或父窗口不在顺序表里）走"恒置顶段"，永远在最上面。

另外两条规则：

- **全屏窗口的选取**：多个全屏窗口时按优先级取最高的。背景是 Wine 切换显示模式时会把一堆旧窗口也标成全屏，顺序还不确定——之前出现过记事本抢走游戏输入的情况。
- **任务栏置顶**：窗口被提到前面后，任务栏会被压回顶部；但**全屏游戏例外**（游戏必须盖过任务栏）。

## 三种显示形态

原生侧只有一个模式位 `desktop`：真 = 虚拟桌面，假 = 多窗口/PC 模式。判断具体行为时用命名查询，不要直接判这个位（代码里有约定，新增分支要用命名查询）。

| 行为 | 虚拟桌面 | 多窗口 / PC |
|---|---|---|
| 画面承载 | 全部合成到一个全屏画面 | 每个窗口独立渲染 |
| 子表面 | 合成进桌面帧 | 登记为弹出层，交给系统子窗口 |
| 输入 | 合成器自己按坐标找目标窗口 | 交给系统窗口系统路由 |

**多窗口模式的一个判据**（内嵌客户区 vs 越界浮层）：靠协议特征区分，不猜——

- 客户区子表面：**输入区域为空**（父窗口接管所有指针事件）且**从不设 viewport 源** → 合进父窗口的帧。
- 其他（菜单、浮层）：每次提交都设 viewport 源（对齐 padding 用）→ 保留独立系统子窗口，可以越出窗口边界。

这个判据是无启发式的（只看协议字段），所以稳定。之前用过启发式（看尺寸、看位置）出过问题。

## 桌面根窗口识别

**为什么需要**：虚拟桌面模式下所有内容合成到根窗口的帧上，其他窗口只在它之上叠加。根窗口是谁决定了取帧路由、渲染器绑定、工作区高度（任务栏位置）。

**怎么识别**：Wine 会把桌面窗口（`#32769`）标记为 `explorer.exe.desktop-shell`，合成器按这个标识 + **标题非空**来认。

**标题是唯一能区分真桌面和"影子"的信号**：Wine 里还有个同样铺满屏幕的辅助窗口（空标题），尺寸和真桌面完全一样——试过用"铺满屏幕"当判据，结果影子窗口顶替了真桌面，桌面背景和任务栏都消失了。

**两个已知的时序问题**：

- 第一次提交可能比标题先到，那次识别不出根窗口（现在靠"桌面未就绪不冻结光标"兜底，没有专门修）。
- 桌面退出时窗口尺寸会波动（系统的中间状态），如果拿这个尺寸去反写输出尺寸，会把输出尺寸弄脏（热重启后桌面高度少 78 像素）。修复：**输出尺寸只由界面层设置，根窗口的尺寸变化不许反写**。

## 状态管理

### 生命周期按"会话"算，不按"进程"算

合成器活在应用主进程里，跨多次 Wine 启动/退出。**任何"只初始化一次"的字段都会跨会话残留**，这是踩过的坑：

- 首帧标记没重置 → 热重启后桌面不激活。
- 根窗口的渲染器泄漏 → 两个渲染循环同时抢帧 → 画面"慢一拍"。

现在的做法：状态按"Wine 会话"建模，会话结束/桌面根窗口销毁时统一重置（`ResetSessionState`）。

**重置范围有讲究**：只重置"进程级的一次性状态和会漂移的状态"（首帧标记、拖动状态、输入焦点和按键状态）；那些"随窗口销毁自然就没了"的字段（根窗口标识、任务栏标识）不在这里清——清了反而会造成锁外写、锁内读的竞态。

另有一条硬规矩：**Wayland 线程里禁止同步等待渲染线程结束**（会永久卡住事件循环）。渲染器的销毁只能由界面层的 surface 销毁回调触发。

### 首帧处理

会话开始时要主动注入一次指针/键盘进入事件——Wine 在用户操作之前就需要这个，否则它不知道鼠标在哪。这个用一次性标记控制，只做一次。

## 设计原则

代码注释里声明的不变量（改代码时要守住）：

- 根窗口的帧是合成基底，其他窗口的帧只在其上叠加，**永不替代**。
- 层序只有一份（合成和输入遍历同一个列表）。
- 输出的尺寸只由界面层设置。
- 帧的几何信息由"交付契约"携带（帧对象自己说明自己的坐标空间和尺寸），消费方**不要再去反查窗口状态重算**——之前因为重算坐标空间出过输入二次缩放的事故。

重构时定的红线（见 [../archive/COMPOSITOR_REFACTOR_PLAN.md](../archive/COMPOSITOR_REFACTOR_PLAN.md)）：

- 不替换自研合成器这个架构（决策见 [../decisions/0001-self-built-compositor.md](../decisions/0001-self-built-compositor.md)）。
- 重构不做"顺手优化"——任何行为变化单独提交、单独回归。
- 游戏和设备的适配补丁是资产，连同注释完整保留，不许以"简化"为名删除。
- 性能不能回退（锁外绘制不许挪回锁内）。

## 已知问题

1. **叠放顺序的隐患**：提窗口的函数不排除桌面根/背景窗口，点桌面空白时可能把桌面窗口塞进顺序表顶部。目前没有实锤的可见问题，但结构上是个隐患。
2. **全屏偶发黑边**：画面缓冲偶尔停在系统中间态尺寸（跟着中间值做了等比缩放，再被系统拉伸）。卡住后不能自愈。
3. **窗口改变大小后画面不刷新**：没有新帧时跳过重绘，导致旧内容被拉伸显示。已修（尺寸变化强制重绘），但"让 Wine 按新分辨率重新渲染内容"这一半还没做。
4. **全屏窗口优先级**的局限：游戏启动器在游戏之后弹的窗口可能盖过游戏。根因在 Wine 侧的标记方式，要根治得改 Wine。
5. **多窗口模式下弹出菜单的叠放**由系统窗口系统决定（按创建顺序），子菜单链极端情况下可能顺序不对。
6. 全屏直传路径下，半透明的全屏内容会丢失混合（预期不会出现半透明全屏内容，属于"容忍并观察"）。
